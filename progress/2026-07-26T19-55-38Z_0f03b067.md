### Root cause (deliverable 1)

Not a crashed predecessor session, and not "reused worktrees" — both of which the existing
guidance asserted. `setup_worktree` (dev-pod `pod/cli.py`) creates a **fresh** worktree at
`origin/<base>` every launch; `install_agent_config` then runs
`shutil.copytree(bundled, ..., dirs_exist_ok=True)` over `.claude/commands` and
`.claude/skills` from a copy bundled inside the installed dev-pod package, frozen at
dev-pod install time. Pod writes the stale content itself, deterministically, every session.

Verified the worktree content byte-identical to the bundled copies for all seven files.
Scale: **91 of this repo's 116 git stashes** are sessions hand-working around this.

Filed upstream with call site and suggested patch:
https://github.com/FormalFrontier/pod/issues/83 — install_agent_config overwrites
repo-tracked .claude/commands and .claude/skills on every session

### In-repo backstop (deliverable 2)

New `.claude/settings.json` + `.claude/hooks/restore-claude-config.sh`. `SessionStart`,
matcher `startup` only (never `resume`/`compact`, so it cannot eat a meditate session's own
in-progress edits). Backs the pre-restore diff up to `/tmp/pod-claude-staleness-*.patch`,
restores only `.claude/commands` and `.claude/skills`, only tracked files, always exits 0.
Neither `settings.json` nor `hooks/` sits in a directory pod copies over, so the backstop
cannot itself be staled.

Verified end-to-end twice (before and after commit): staled all seven files exactly as pod
does, ran a real `claude -p`, worktree came back clean with a fresh backup patch.

### The measured limit — worth knowing before anyone tries to extend it

Tested in a scratch repo with a marker command and a marker skill whether the hook also
fixes the *served* text. With the hook demonstrably firing and restoring both files on
disk, the agent was served `MARKER=STALE` for the command **and** `SKILLMARKER=STALE` for
the skill. Both are snapshotted at session start, before the hook's writes are visible to
the loader.

So the hook fixes the half that corrupts `main` (the `git add -A` reversion — the 91
stashes) and nothing of the half that misinforms the agent. No in-repo hook can fix the
second half; only the upstream change can. Do not spend another session trying.

### Side finding (reported upstream, not acted on here)

`_pod_installed_files()` adds every bundled command/skill to `POD_PROTECTED_FILES` so
agents "cannot modify pod-delivered files in PRs", but the bundled `coordination` script
contains no reference to that variable, so the restriction is not enforced. Fortunate for
this repo, which vendors and improves those files, but intent and behaviour disagree.
