### Key findings (the map for the successors)

1. **The crux statement is FALSE as written.** It is missing
   `hSne : ∀ i, 0 < Module.finrank k (S i)`. Without it a degenerate decomposition
   with `S i₀ = 0` carries an unconstrained "ghost" abstract simple `L i₀` whose
   character need not be a Schur polynomial (and two ghosts break `Injective lam`).
   The ℂ-variant `schurWeyl_simples_formalCharacter_classification_core_complex`
   (`...Complex.lean:763`, doc at :757) already carries `hSne` for exactly this.
   This is a genuine correctness fix, independent of the wiring.

2. **The math machinery already exists, but ℂ-only and downstream.**
   `SchurWeylSimplesClassificationComplex.lean` is a **leaf** (consumed nowhere —
   verified by grep) proving the full ℂ classification core sorry-free modulo the
   density seam #4932. Its five building blocks
   (`schurWeyl_simples_isotypic_matching_complex`,
   `..._formalCharacter_linearIndependent_complex`,
   `schurWeyl_simple_summand_glWeightSpace_top`, `..._isAlgebraic`,
   `..._classification_core_complex`) are **field-generic** — the ℂ→k port is
   mechanical, swapping `schurModule_isSimple` → `schurModule_isSimple_general`
   (#4946) and `..._torus_trace_eq_zero` → `..._general` (#4947). The helpers
   `schurWeyl_decomposition_asModule_flatten`,
   `formalCharacter_eq_of_asModule_linearEquiv`, and
   `schurWeyl_decomposition_numerical_identity` are **already general-k**. The
   general seam `formalCharacter_simples_coeff_eq_zero_of_torus_trace_eq_zero_general`
   (`SchurWeylFormalCharacterIso.lean:286`) has the exact signature the lin-indep
   proof needs.

3. **The blocker is purely architectural (import position).**
   `SchurWeylSimplesClassification.lean` (the crux) imports only
   `FormalCharacterIso`, so it is **upstream** of every piece of machinery:
   the seam lemmas #4946/#4947 (`SchurWeylFormalCharacterIso.lean`, downstream),
   and the building blocks (leaf complex file, most downstream). The crux cannot
   consume them without an import cycle. The real consumer
   `polynomial_homog_rep_asModule_embeds_directSum_simple`
   (`PolynomialGLDecomposition.lean:423-430`) bakes the classification (`hclass`)
   into its output, but `hclass` is *used* only downstream at
   `iso_of_formalCharacter_eq_schurPoly` — where the seam lemmas live. So #4994
   offers two routes: (1) migrate machinery upstream + discharge in place, or
   (2 preferred) strip `hclass` from the `PolynomialGLDecomposition` API and derive
   the classification downstream, then delete the crux.

4. **General k is genuinely required** (not ℂ-only): `Proposition5_22_2.lean:366`
   calls `iso_of_formalCharacter_eq_schurPoly k N ...` at general `k`.
