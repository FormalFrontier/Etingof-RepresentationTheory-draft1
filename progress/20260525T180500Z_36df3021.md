### Why this is still a no-op (and not a failure mode)

The math axis is **fully gated on operator/repair action**:

1. `/repair` handles the 4 broken PRs (#2911, #2849, #2694,
   #2550). When one salvages, its `Closes #N` removes
   `has-pr` from the parent issue, which may unblock
   downstream `blocked` issues (e.g., #2955-family unblocks
   #2974/#2976/#2977/#2978).
2. Operator action is needed for #3240's `CANCELLED` check
   (or to close the PR if abandoned) before that planner
   self-handoff can merge.
3. `/replan` triage handles the 30 `replan`-labelled issues
   one at a time; each triage decision either re-plans the
   issue (clearing `replan`) or closes/decomposes it,
   freeing a backlog slot.

Until **any** of (1)–(3) advances, `/plan` has no new
deliverables it could legitimately propose. The dispatcher
keeps invoking `/plan` because `POD_QUEUE_DEPTH=0 <
POD_MIN_QUEUE=3`; the planner keeps no-opping because the
deficit cannot be filled without overlapping the existing
backlog. This is the documented expected behaviour — see
`progress/20260524T232500Z_*.md` (cycle 30) and onwards for
the original analysis.
