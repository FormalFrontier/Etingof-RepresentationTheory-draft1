### Filter-reading correction (carried forward)

Cycle 1106's progress file said #4341 was *excluded* from
the Step 2 mergeable filter because "the rollup contains
only QUEUED entries (empty conclusion ≠ non-failure)".
That's wrong. The filter clauses are:

1. `mergeable == "MERGEABLE"` — #4341 satisfied this.
2. `(.statusCheckRollup | length > 0)` — #4341's rollup
   was `["", ""]`, length 2 ≥ 1, satisfied.
3. `(.statusCheckRollup | all(.conclusion != "FAILURE"
   and .conclusion != "CANCELLED"))` — empty string `""`
   is `!= "FAILURE"` (true) AND `!= "CANCELLED"` (true),
   so `all` is true, satisfied.

All three clauses passed. The filter does *not* require
checks to be `SUCCESS`; it only excludes `FAILURE` and
`CANCELLED`. PRs with `QUEUED` checks (empty conclusion)
are eligible for the merge attempt, and `gh pr merge
--squash` will fail with `mergeStateStatus=UNSTABLE` if
the checks haven't yet succeeded — but in #4341's case,
GitHub's auto-merge had already landed the PR before this
cycle ran, so the merge attempt was a no-op rather than
a failure. Future planners should expect that PRs with
QUEUED checks pass the filter; either GitHub auto-merge
beats the planner to it (no-op), or the explicit
`gh pr merge --squash` fails cleanly on `UNSTABLE`.
