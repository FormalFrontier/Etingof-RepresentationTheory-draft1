### The conflict was not an ordinary one, and the obvious resolution is wrong

`git merge origin/main` conflicted in two hunks of `SKILL.md`, but resolving just those
two hunks produces a **silently corrupted file**. The merge base (`ad719080`, 318 lines)
predates the whole "stale worktree / unmerged-PR dependency" section. Both sides then
grew an evolved copy of that section independently, so git's three-way merge saw it as
add/add on the two hunks it flagged and as *two unrelated additions* everywhere else —
it concatenated them. The result had the entire Step 2 block duplicated verbatim
(`grep -c "Before that .git reset --hard"` returned 2 where both parents return 1) with
no conflict markers anywhere near it. Anyone resolving only the marked hunks and running
`git status` would see a clean tree and ship a 700-line skill with a 60-line paragraph
repeated.

**Tell for this situation:** the merge base lacks a section both parents have. Check with
`git show $(git merge-base HEAD origin/main):<path> | grep -c "<a distinctive line>"`
returning 0 while both parents return 1. When that holds, do not resolve hunk-by-hunk —
pick one side's file wholesale and re-add what the other side uniquely has.
