### Why this is still a no-op (and not a failure mode)

The math axis is **fully gated on operator/repair action**:

1. `/repair` handles the 4 broken PRs (#2911, #2849, #2694,
   #2550). When one salvages, its `Closes #N` removes
   `has-pr` from the parent issue, which may unblock
   downstream `blocked` issues.
2. Operator action is needed for #3240's `CANCELLED` check
   (or to close the PR if abandoned).
3. `/replan` triage handles the 30 `replan`-labelled
   `feature` issues (plus 1 `human-oversight,replan`) one
   at a time; each triage either re-plans (clearing
   `replan`) or closes/decomposes the issue, freeing a
   slot in the plannable queue.

The planner correctly cannot create new feature work
that would overlap the existing 45 issues. Creating
parallel issues for the same items would be a real
failure mode (duplicate work, conflicting PRs); a no-op
handoff is the correct response.

### Why no `return-to-human`

`return-to-human` requires zero broken PRs. The 4
`CONFLICTING` / `FAILURE` PRs in `/repair` scope keep the
project out of fully-converged state. The `/repair` agent
loop owns those, not the planner.

### Why no `set-target`

Per `/plan` Step 6: only call `set-target` when fully
converged (call `return-to-human` instead) or in the tail
phase with a small number of in-flight streams that future
planning genuinely depends on. Neither applies here. The
project is steady-state idle on the math axis with
`/repair` and `/replan` holding the only active work
streams — shrinking the agent pool would starve them.
