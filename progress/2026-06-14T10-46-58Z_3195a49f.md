## Portability caveats for downstream porters (#4554, #4551, d5 #2850/#2851, d7 #4533)

1. **The proj siblings handle only the *reversed* (clean-pull) leaf.**
   They extract one component with no N-twist. In a mixed-direction
   branch (one leaf edge canonical, one reversed — combo C/C′), the
   *canonical* leaf arrives as a push `γ(embed·)` carrying the `Ny`
   twist; the proj sibling does nothing for it. The genuine obstruction
   #4554 must solve is the canonical (push) side, not the reversed side.
   Do not expect a proj sibling to discharge a mixed branch on its own.

2. **Combo D's avoidance trick is orientation-specific.** It works only
   because *both* v=4 leaves are reversed, so both pulls are clean and the
   N-twisted containment can be routed around. Porters cannot reuse this
   routing for the mixed cases.

3. **Leaf-side convention is invariant across the family.**
   `starEmbed1_F`/`starFirst_F` ↔ "1-side" leaf; `starEmbed2_F`/
   `starSecond_F` ↔ "2-side" leaf. The v=2→v=4 shift is {2↦4,0↦5,1↦6};
   keep this map intact when porting to d5 {…} / d7 {…}.

4. **No orientation-convention mismatch.** Canonical v=4 direction is
   leaf→branch (`5→4,6→4`, leaves inward); reversed is branch→leaf
   (`4→5,4→6`) via starFirst/starSecond. This agrees with the universal
   sink-orientation pattern (`dTildeQuiver`, leaves point inward as
   canonical). No mismatch against `dTildeOrientation`.
