## Current frontier

The residual sorry is `crux` in `extAbelianIsoExtₖ.map_smul'`
(`Chapter8/ExtAbelianComparison.lean:145`):

```
crux : ∀ (f : P.complex.X n ⟶ N) (hf : P.complex.d (n+1) n ≫ f = 0),
    e123 (P.extMk (r • f) (n+1) rfl _) = r • e123 (P.extMk f (n+1) rfl hf)
```

where `e123 = extAddEquivCohomologyClass ≫ homologyAddEquiv.symm ≫ homComplexHomologyAddEquivₖ`.

**Why it is hard (confirmed by investigation).** The `r`-scalar lives as the `k`-module action on
the hom-group `P.complex.X n ⟶ N`, which the middle types (`Cocycle`, `CohomologyClass`,
`homCochainComplex.homology`) are all `AddCommGrp`-valued and *forget*. The `k`-structure only
reappears on the target `(linearYonedaObj).homology n`. So the content is: the additive tower
`homComplexHomologyAddEquivₖ` (built in `HomComplexHomologyK.lean` from `homDegEquiv`/`sIso`/`scIso`/
`homIso`, cased `n=0` vs `n=m+1`) is *secretly `k`-linear* on these elements. There is no Mathlib
naturality API for `homologyAddEquiv`/`CohomologyClass` under a target morphism.

**Suggested decomposition of `crux`** (documented on #6943):
- (step 1) `extAddEquivCohomologyClass (extMk g) = CohomologyClass.mk (Cocycle.toSingleMk (xiso.hom ≫ g) …)`
  via `extEquivCohomologyClass_extMk` (mechanical).
- (step 2) class-level formula for `homologyAddEquiv.symm (CohomologyClass.mk c)` via
  `CochainComplex.HomComplex.leftHomologyData` (`π = CohomologyClass.mkAddMonoidHom`).
- (step 3, the beast) the `homIso` tower sends the `homDegEquiv`-image class of `g` to the
  `linearYonedaObj` homology class of `g`, degreewise `k`-linearly; case `n=0`/`n=m+1`.
